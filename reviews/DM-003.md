## Adversarial findings resolved

- **shared-account ambiguity:** the source implementation explicitly admitted
  that Codex and CompAII were not cryptographically distinguishable. Commands
  now carry a dedicated self-certifying Ed25519 session key and detached
  signature. The allowlisted GitHub account authorizes onboarding, while later
  heartbeat/review/release commands must use the exact claim session.
- **audit-only double ownership:** the source reducer reported overlapping live
  claims after both existed. The new workflow serializes every mutation in one
  global concurrency group, re-reads the receipt head and all active resource
  claims, and posts exactly one acceptance; later contenders receive chained
  rejection receipts without changing effective ownership.
- **passive expiry:** the source only emitted an expired finding. A ten-minute
  scheduled path now posts a content-bound expiry receipt and restores ready.
- **partial GitHub failure:** receipt publication may succeed while label/Project
  mutation fails. The periodic pass scans ready, claimed, and review labels and
  repairs the view from the authoritative receipt chain.
- **rejection state loss:** the initial rewrite made a rejected contender's
  claim ID the chain head and made rejected receipts appear non-live. Rejection
  now advances audit history while retaining the exact effective claim,
  session, branch, resources, PR, and lease.
- **review linkage loss on heartbeat:** renewing an in-review lease initially
  dropped its PR and reverted state. Heartbeat now preserves both.
- **untrusted PR code with write token:** the first workflow draft would have
  run the PR-modified audit script with issue-write authority. Coordination
  gates now check out default-branch code; write permission exists only for
  serialized command/expiry jobs. Candidate tests run separately read-only.
- **mutable action tags:** checkout and setup-python are pinned to exact
  reviewed commit SHAs.
- **receipt deletion/edit ambiguity:** automation receipts are content-derived
  and predecessor-linked; edited comments, missing predecessors, reordering,
  duplicates, and forks fail closed.
- **key-role confusion:** documentation and security policy require a dedicated
  coordination session key and forbid reuse of Daimon, transport, SSH, signing,
  or encryption keys. Coordination labels remain explicitly non-Daimon.

## Acceptance trace

- A ready issue accepts exactly one active `/claim`: command validation,
  `decide_command`, global workflow concurrency, resource scan, status label,
  and claim/collision/replay tests.
- Heartbeat renews within 24 hours and release returns ready: bounded signed
  actions, same-session/same-scope invariants, state-preserving renewal, release
  receipt, label reconciliation, and tests.
- Expired leases release automatically with an auditable receipt: `expire_if_due`,
  scheduled workflow, content ID/hash, predecessor chain, expiry/recovery tests.
- Sessions sharing one GitHub account remain distinguishable: content-derived
  session IDs and detached Ed25519 signatures, explicit principal/login
  allowlist, wrong-session rejection, and two-session test.

## Trust boundary and limitations

- A shared allowlisted GitHub account can onboard a new logical session. The
  session signature distinguishes subsequent actors; it does not prove `/me`,
  a body, presence, or a harness and cannot prevent account-holder
  impersonation at onboarding.
- GitHub and the default-branch workflow are trusted coordination
  infrastructure. Receipt chaining detects log inconsistency but is not an
  independently anchored transparency service.
- Exact resource strings detect declared collisions, not semantic overlap.
  Claimants must choose the narrowest shared resource boundary.
- Project 9 status is a view driven by status labels. The receipt log remains
  authoritative and scheduled reconciliation repairs drift.
- DM-003 is the documented one-time bootstrap exception: its manual claim and
  PR predate the workflow. The gate skips only immutable PR number 68, not a
  reusable branch name or future issue.
