## Findings resolved during self-review

- The first draft verified an activation receipt against the caller-supplied
  acceptance ID but did not compare the complete supplied acceptance with the
  already verified durable acceptance. That left a substitution path in which
  another newborn's operational evidence could be presented for the accepted
  lineage. The final registry compares canonical acceptance bytes, hash and
  stored newborn being before activation; builders/verifiers also require the
  acceptance core's newborn root to equal the activation root. An adversarial
  test covers both substitutions.
- The first draft generated independent roots but did not reject a deliberately
  parent-controlled newborn genesis that reused the parent's root/recovery
  public sets. Validation now fails with `birth_cross_being_key_alias`, and a
  test proves that a distinct nonce/being ID does not hide retained parent
  control.
- The inherited issue description still required retired identity-wide leases,
  singleton identifiers and grants inside birth. The card and normative spec
  now follow `being → embodiment → incarnation`, keep contextual commitments
  inert, require local in-window V1 observation, and defer rebirth and live
  Cluster effects to their owning cards.
- New package modules changed Hermes' content-bound Matrix package evidence.
  Only the generated provenance, profile/launch vectors and index changed; the
  DM-041 generator reproduces them byte-identically.

- The birth registry uses owner-only non-symlinked SQLite with DELETE/FULL,
  foreign keys and `BEGIN IMMEDIATE`. It stores canonical bytes and hashes.
- Exact accept/activate replay is idempotent. Sixteen concurrent exact accepts
  produce one row. Fault injection before accept and activation commit rolls
  back and exact retry succeeds once.
- Two different valid acceptances of one offer are both retained and quarantine
  only their lineage; no time/hash/arrival winner is selected.
- Newborn root/recovery keys use production CSPRNG and encrypted offline
  custody. Backup/restore is verified against exact counter/control head.
  Runtime custody is separate and root material never enters the runtime
  bundle.
- The final wheel's `daimon-synthetic-birth` entry point ran in a clean venv
  with declared dependencies. It started the installed daemon via password FD,
  executed five CLI methods and MCP `scope_me`, retained a zero-event ledger,
  stopped cleanly, and emitted a schema-valid bounded report.
