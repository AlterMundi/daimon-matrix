# Tribe scope, learning and software delivery

Nicolas reaffirmed this distinction on 6 November 2026. The pinned
[foundation](../foundation/daimon-matrix.md) remains unchanged: `/tribe` is the
endpoint for the daimons **and humans** with whom an identity pairs or shares
resources. `/we` is that being's own plural bodies. Shared ancestry does not
make Eko or Oliva part of CompAII's `/we` or merge their private histories.

The retired Tribe Bridge, the current membership conversation and its valid
incoming/outgoing channel identifier `tribe` are not synonyms for `/tribe`.
Keep those identifiers and historical originals. Describe a messaging operation
as messaging, rather than redefining the whole social/resource scope around it.
`scope.tribe` currently resolves signed membership and separately authorized
resources; that implemented view does not establish complete human endpoint,
resource discovery, software rollout or autonomous coordination support.

## Use the existing path that owns the effect

| Need | Existing path | What remains separate |
| --- | --- | --- |
| Identify participants/resources | `scope.tribe`, membership and relationship resource cards/grants | Reachability, disclosure and permission for a concrete operation |
| Exchange same-being evidence | `/we.diff`, `/we.sync`, signed Weave heads/events and local adoption decisions | Materializing memory, configuration or software; actual model context |
| Offer selected cross-being learning | Source claim/publication, authorized diff, `incoming`, `pull` into quarantine, local assessment and promotion | Trust/adoption by each receiver, selective installation and use |
| Review available offers | Existing bounded Source review and known/status/projection reads | Content transfer, installation, model attention and fresh remote convergence |
| Install portable skills | Exact reviewed Skills commit/descriptor, selective `prepare/apply/status/recover/rollback` | Harness discovery/reload and actual use in a receiving model |
| Apply native memory/behavior deltas within one being | Existing same-being integration operator with exact proposals, decisions, owning adapters and effect receipts | Cross-being autobiography, arbitrary app deployment and consumed model context |
| Deploy app/backend/SDK software | Owning repository release and receiver maintenance route, current placement, qualified candidate and compatible rollback | Publication/notification is not deployment; service health is not device acceptance |

Source project publications are attributed learning references, not species or
ancestry selectors. The foundation's ancestry `/source.pull` and
`/species.pull.name` must keep their lineage meaning; species release/live
adoption remains deferred and does not gate routine software updates.
A Source promotion currently projects an external reference; it does not run
an installer. Weave preserves proposals, decisions and observed projection
receipts; a signed record alone cannot execute an external effect.

For routine SDK delivery use Cluster's existing
[successor route](https://github.com/nicoechaniz/daimon-cluster/blob/main/docs/runbooks/tribu-sdk-successor.md),
including current group-reader qualification after a reload. For skills use the
[selective update route](shared-skill-updates.md). Neither route requires a chat
message as its only distribution surface. Publish reusable source and operator
instructions in the owning project so another authorized operator can maintain
it without contacting its author. Preserve receiver-specific configuration and
local changes; no blanket overwrite, identity replacement or private-memory pool.

## Current limits and unfinished support

The current authenticated ITACA foundation client exposes scope, Source observer
and Weave read/preview operations. Advertised methods are not a grant to mutate,
fetch foreign private history, install content or start a model. Resolve actual
owner rights and retained results before each selected effect. The local known
Sources view reports retained evidence, not a tribe-wide fresh update catalog.

A single general operator connecting selected cross-being software offers to
all owning application installers, receiver decisions, resumable deployment and
actual harness/model uptake is not established by these mechanisms. The
same-being integration work still has behavior/materialization and actual
receiving-use gaps; it is not a generic cross-being app updater. Full human
membership/endpoint coverage and automatic future onboarding likewise remain
partial. Track these gaps in the existing foundation roadmap (#302/#437) and
owning component issues, without creating another catalog or approval framework.

DaimonApp owns its voice/API and application receiving/fleet implementation.
Matrix supplies the scope/identity/evidence contracts and existing shared routes;
this clarification starts no duplicate application implementation. Heartbeat
messaging activation and pause controls are separate unfinished work. No timer,
autonomous reply, model wakeup or global Stop follows from this document.

Keep evidence precise: **published → available/received → assessed/selected →
installed/loaded → actually used**, recording only observed steps and unavailable
receivers. Reuse one owning checkpoint; these distinctions are facts, not extra
permission gates or mandatory ceremonies.
