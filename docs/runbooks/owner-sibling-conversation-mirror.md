# Owner-selected sibling conversation mirror

This optional installation mirrors one being's `/we` conversations to its
explicitly selected Telegram destination. Siblings remain embodiments of the
same being: no relationship, tribal grant or second being is synthesized.
Scope resolution and state convergence remain private. This option does not
permit inbox polling, autonomous replies, model wakeups or background sends.

## Prepare and qualify

1. Use the existing body's canonical SDK installation, signed public bundle,
   current authority and authenticated owner-local client. Preserve its custody,
   ledger, incarnation and existing peer targets. Verify that the signed client
   capability actually includes `we.converse` and the required conversation-read
   operation; this installation cannot widen an old capability bundle.
2. Prepare a private owner-only visibility directory. Use the existing visibility
   installation schema and genuine body binding operations. Select scope mode
   `all-inter-daimon-and-sibling-conversations`, projected content
   `complete-plaintext-content-and-metadata`, and risk
   `all-inter-daimon-communication-and-sibling-conversations-will-be-posted-as-plaintext-to-the-fixed-telegram-destination`.
   Bind the actual local application digest expected by the daemon. Disclose both
   directions and the actual fixed bot, chat, topic and representation. For an
   exclusively same-being channel, disclose that same being once and obtain its
   genuine acceptance; do not invent a relationship or another participant.
3. Qualify that exact token, bot and destination with the official Telegram
   transport, including an explicitly authorized bounded probe post. Retain the
   actual returned message ID, probe-text digest and token digest. `getMe` and
   `getChat` alone, another body's old qualification, or a fabricated message ID
   do not qualify this installation. Never expose the token or signing keys.
4. Verify every participant's binding over the complete disclosure, its scope
   digest, the acceptance-set digest, and the owner binding over the complete
   installation. Use the official visibility loader with genuine verifiers and
   its expected application digest. Keep token/proof files owner-only. An old
   disclosure acceptance cannot authorize the new mode.

## Catalog preflight

Before activation, qualify the new installation against copies of every actual
native catalog using the official loader and full history reconciliation.
Closed-visibility catalogs use a different authentication key from an owner
installation. The existing schema-provisioning migration does not change that
key. Consequently, an existing closed catalog can refuse the new installation
with `egress_catalog_invalid` even when its schema is current. Do not delete its
obligations, use a public zero key for a live owner installation, rewrite their
bindings or report schema migration as authentication migration. Such a body
needs a separately qualified owner-authorized transition that preserves all
accepted native/echo history before this mirror can be activated.

## Activate and verify

Replace only the existing body's reviewed visibility startup selection with the
qualified installation and restart its existing daemon once. Revalidate its
original identity, authority, ledger and owner health. If Cluster tracks the
physical daemon process, refresh its observation profile against the actual new
PID, start time, boot ID and socket credentials using the current native
procedure. A stale process profile must refuse; never substitute a guessed PID,
rewind Registry history or restart an incompatible old Registry writer.

Send one human-authorized bounded `/we` message through the rendered owner client
or supported structured SDK operation. Retain its request ID before submission.
Verify genuine sibling delivery and the local confirmed Telegram echo, including
full text, original author embodiment, message ID, recipient and thread. The
request and response paths each enforce their own body's configured policy;
when both bodies opt in they may echo the same message twice. Projection reads
an authorized carrier copy and does not count as intake or receipt authoring.

A confirmed echo is reused on retry. If a Telegram result is ambiguous, retain
its operation and use the existing genuine owner ambiguity-recovery procedure;
never blindly repost or submit the message with a fresh ID. A failed echo blocks
the corresponding native request/response egress. An inbound message can already
be retained before its mirrored response is released; that retained history is
not rolled back. Verify scope/sync still produce no Telegram posts.

## Recovery and limits

Retain the original startup selection and exact installation files before
activation. Recover by restoring the explicitly authorized configuration and
coherently refreshing process observation after any restart, preserving all
accepted ledger, echo and Registry history. Switching an installation does not
re-authorize old retained obligations under a different disclosure or policy:
inspect and resolve existing queued or ambiguous operations before cutover.

Default closed visibility and the existing `all-inter-daimon-communications`
installation retain their prior behavior. The opt-in proves visibility and
current authority; it grants no Root custody, capability renewal, model access
or autonomous operation. Operational acceptance requires actual delivery and
actual Telegram receipts, independently of source tests and CI.
