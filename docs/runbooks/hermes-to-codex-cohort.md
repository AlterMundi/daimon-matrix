Codex bodies on daimon-cluster. Each human must be able to SSH into their own
environment, type ordinary `codex`, and converse through a dedicated Telegram

launcher or relying on operator memory.

another being's self-definition. The receiving context combines the selected
shared definition with that being's own SOUL and actual body instructions.

one parent branch release and its birth offer has one parent being. A signed
multi-parent recombination ceremony is not currently implemented. The species
contract also retains an obsolete `/we -> distinct /me -> one active body`
sentence; reconcile it with the maintained ontology before using that contract.

Birth activation proves a zero **Matrix autobiographical ledger/projection**
cutoff. That is not permission to erase a legacy HMK corpus and is not evidence
that retaining HMK is impossible. Preserve the archive first, determine whether
there is an existing Matrix being root, and select the appropriate enrollment,
continuity and attributed import sequence. Do not sign a false empty-state

## Preserve the complete HMK corpus

1. Inspect the configured HMK wrapper, actual database/base, installed commit
   or version, schema, retrieval/embedding provider and credentials' ownership.
   An old version is a hypothesis until inspected. Inventory the complete
   authorized HMK tree, referenced material and databases; include sources,
   chapter/link/provenance data, indexes/embeddings and retained history. Keep
   inventories, paths, contents and hashes private. Preserve original SOUL
   versions and historical skills in the same private migration archive.
2. Before mutation, create a coherent SQLite API snapshot of every live HMK
   database and verify integrity and foreign keys. Quiesce all relevant writers
   for a coherent final tree/archive, including journal companions where
   applicable. Copying a changing SQLite tree is not a verified backup. Record
   file hashes, schema, logical per-table contents/counts and the snapshot's
   cutoff; verify the received archive before opening it for writes.
3. Restore the full authorized corpus into that same being's isolated target
   pool. Preserve the source archive unchanged. Do not filter it into a summary,
   select only recent chapters, mix it with CompAII/another being, or turn legacy
   memories into events signed as lived by the new body. Existing signed
   projections retain their source authority; HMK-native and legacy material
   retain their own provenance. Matrix custody, credentials and writable
   runtime journals use their separate supported enrollment/transfer contracts.
4. Determine whether the selected HMK release can open the inspected schema.
   Use its supported migration on a backed-up target copy only when needed;
   keep original and migrated artifacts distinct. Preserve every record's
   content, identifier, relationship and provenance through the supported
   mapping. Compare logical content as well as counts; changed schema layouts
   alone cannot prove loss or preservation. Do not run `init` over an existing
   corpus, drop tables to get a green startup, or silently change providers or
   re-embed the corpus. An unsupported schema is a concrete launch blocker
   requiring a supported correction and a retained original.
5. Render the being's neutral HMK wrapper/binding and confirm it resolves the
   intended pool. Run integrity/statistics and human-selected lexical/hybrid
   retrieval on representative older and newer records, links and provenance.
   Provider credentials belong to that owner. Record storage and retrieval
   results separately if an embedding service is unavailable. Verify target
   writes land only in the selected target and preserve the agreed source cutoff.

Rollback before target writes restores the previous source binding/service and
keeps the receiving copy for inspection. After target writes or new human input,
retain and reconcile those new records before changing write authority. An older
source snapshot must never erase target memory, accepted Telegram input or
Matrix history. Source deletion is a separate explicit retention decision.
